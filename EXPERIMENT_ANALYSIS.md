# Experiment Analysis Workflow

This document outlines the standard workflow for interpreting experimental results in the Masa repository. Follow these steps to systematically analyze performance data, verify behaviors with logs, and formulate next steps.

## 1. Understand the Experiment Configuration

Before looking at the results, you must understand what was tested.

*   **Config Path:** `exp/<app>/data/in/<experiment>/gen_config.json`
*   **Alternative Path:** A copy is also saved in each output directory: `exp/<app>/data/out/<experiment>/<run_id>/<policy>/gen_config.json`

**Key aspects to check:**

*   **Policies:** What scheduling policies are being compared?
    *   Check the `policies` file in the experiment input directory (e.g., `exp/<app>/data/in/<experiment>/policies`).
    *   Common policies: `fifo`, `fifo,early`, `prio_local,early`, `prio_oldest,early`.
*   **Service Graph:**
    *   **Synthetic:** Defined in `config.docker.json` (look for the `call_graph` object defining services and call sequences).
    *   **MSSim:** Defined in `mssim.json` (look for `callgraph_dirs` which points to the trace directory containing the graph structure).
    *   **Real Applications (Hotel, SocialNet):** Fixed topology defined in the application source code (`apps/hotel`, `apps/socialnet`).
*   **Workload:** What are the processing times (`mean_service_time_us`) and payload sizes? Are there distinct request types?
*   **SLO:** What is the end-to-end deadline?

## 2. High-Level Result Interpretation (Plots)

Start with the aggregated metrics to get the "big picture" of performance.

*   **Plots Directory:** `exp/<app>/data/plots/<experiment>/`
    *   *Note: This directory usually contains both PNG images and CSV summaries.*

**Key Files to Analyze:**

Here are a suggested list of things to look for. Feel free to analyze other things that you find interesting, in addition to these.

| File Name | Purpose | What to Look For |
| :--- | :--- | :--- |
| `goodput_ALL_aggregated.csv` | Overall Throughput | **Saturation Point:** At what RPS does goodput stop increasing?<br>**Max Goodput:** Which policy achieves the highest peak goodput?<br>**Collapse:** Does performance degrade significantly after saturation? |
| `latency_summary_ALL.csv` | Latency Stats | **SLO Compliance:** specific attention to p99 latency. Does it stay under the deadline? |
| `early_return_ALL_breakdown.csv` | Load Shedding | **Drop Location:** Which services are performing the drops? (Frontend vs. Leaf/Child)<br>**Drop Rate:** How does the drop rate correlate with goodput? |

## 3. Deep Dive & Validation (Logs)

Once you have high-level observations (e.g., "Policy A drops requests at the frontend"), verify them using the raw logs.

*   **Logs Directory:** `exp/<app>/data/out/<experiment>/<run_id>/<policy>/`
    *   *Note: `<run_id>` is usually `0` for single-run experiments.*

### A. Analyze Raw Traces (`r<RPS>_a.csv`)
These files contain a line for every request generated by the load generator.

*   **Verify Drop Locations:**
    Use `grep` to find specific error messages indicating where drops occurred.
    ```bash
    # Example: Count drops by "EarlyReturn" mechanism
    grep "/EarlyReturn" exp/synthetic/data/out/exp2/0/prio_local,early/r1200_a.csv | head
    ```
    *   *Observation:* If drops are at `frontend.Frontend`, the policy is reactive (likely checking only on return). If drops are at `child.Child`, the policy might be predictive or checking deep in the graph.

*   **Check Latency Distributions:**
    Look at the latency column (usually near the end) for successful vs. failed requests.

### B. specific CPU Utilization (`cpu_stats.csv`)
Correlate performance with resource usage.

*   **Saturation Check:** Are services hitting 100% CPU?
*   **Efficiency:** If two policies have the same CPU usage but different goodput, one is doing "more useful work" (better scheduling/dropping).
    *   *Example:* `prio_local,early` often shows high CPU (saturation) but higher goodput than `fifo,early` because it spends that CPU on requests that will actually meet the deadline.

### C. Container Logs (`logs/*.log`)
Check these if behavior is inexplicable (e.g., zero goodput, sudden crashes).
*   Look for panics, connection resets, or explicit warnings from the application code.

## 4. Formulating Hypotheses & Actionable Next Steps

End your analysis by synthesizing your findings into a hypothesis and proposing the next step.

**Example Actionable Next Steps:**

1.  **New Experiment Config:**
    *   *Idea:* Try a deeper call graph to exacerbate the wasted work issue.
    *   *Action:* Create `gen_config_deep.json` with `depth: 5`.
    *   *Reasoning:* If `prio_oldest` is dropping at the frontend, it implies the wasted work is happening in the children. A deeper graph increases the cumulative service time and the probability of a deadline miss occurring mid-chain. If the hypothesis is correct, `goodput` should degrade faster with depth for `prio_oldest` than `prio_local`.

2.  **Instrumentation:**
    *   *Idea:* We need to know exactly *when* the deadline check fails in the child.
    *   *Action:* Add a log line in `libs/tonic/.../server.rs` printing `remaining_time` when a request arrives.
    *   *Reasoning:* `early_return_ALL_breakdown.csv` shows 0 drops in child nodes for Policy X, despite high latency. This suggests children are processing requests that are already dead. Explicit logging of `remaining_time` at ingress will confirm if negative values are being ignored or if the deadline is just very tight.

3.  **New Metrics:**
    *   *Idea:* Is the queue time dominating?
    *   *Action:* Instrument `MasaHooks` to measure and plot `queue_time` vs `service_time`.
    *   *Reasoning:* High `cpu_stats.csv` (100%) but low goodput suggests requests are spending time in the scheduler queue. If `queue_time` > `service_time`, the bottleneck is queuing delay, confirming that we need a policy that reorders the queue (like `prio_local`) rather than just faster processing.

---
*Be objective. If the data is noisy or inconclusive, state that clearly rather than forcing a conclusion.*
